# Resources

AI-assistant resources shipped inside the binary. Phase 4 split the
single `resources/` root into two parallel trees — the **orchestrator**
side (this directory) and the **skills** side under `skills/resources/`
(gap-filling skills, mirroring pattern). Within each side, the Claude
tree is auto-generated from the OpenCode tree.

## Layout

```
(project root)
├── orchestrator/                                # orchestration-side root
│   ├── source/                                  # Python CLI engine
│   ├── core/                                    # vendored openspec-core subtree
│   └── resources/                               # ← THIS directory
│       ├── AGENTS.md                            # (you are here — top-level)
│       ├── opencode/                            # OpenCode platform (canonical)
│       │   ├── manifest.toml                    # Per-resource version manifest
│       │   ├── skills/osx-*/                    # Skills (workflow + phase commands)
│       │   ├── agents/osx-*.md                  # Orchestrator-dispatched agents
│       │   └── commands/osx-*.md                # Slash commands (single-emit)
│       └── claude/                              # Claude Code (auto-generated)
│           ├── manifest.toml                    # Mirrored from opencode
│           ├── skills/osx-*/                    # Mirrored skills
│           ├── skills/osx-*/SKILL.md            # PLUS, dual-emit (legacy form)
│           └── commands/osx/<name>.md           # Legacy dual-emit
└── skills/                                      # skills-side root
    └── resources/                               # parallel tree (see below)
        ├── opencode/                            # Gap-filling skills + commands
        │   ├── manifest.toml
        │   ├── skills/osx-{commit,review-artifacts,review-test-compliance}/
        │   └── commands/osx-{review,verify-tests}.md
        └── claude/                              # Mirror of skills/opencode
            ├── manifest.toml
            ├── skills/osx-{commit,review-artifacts,review-test-compliance}/
            ├── skills/osx-{review,verify-tests}/  # dual-emit of the commands
            └── commands/osx/{review,verify-tests}.md
```

## Phase 4 split rationale

Pre-Phase-4 the project had a single `resources/` root mixing two
concerns — autonomous workflow resources (skills that drive the
7-phase orchestrator) and utility/gap-filling skills (review, commit,
verify-tests). Phase 4 separated them so each side can version and
ship its own manifest independently. Phase 5 will rewrite the deploy
loop to consult both trees; Phase 4 keeps the deploy loop using just
the orchestrator-side manifest at `get_resources_dir()` (back-compat
for the current binary contract) and adds a parallel helper for the
skills side.

## Claude mirror

`resources/claude/` (and `skills/resources/claude/`) are generated by
`mise run sync:mirrors` (and verified by `mise run sync-mirrors --check`).
OpenCode is canonical; edit there, regenerate, commit both. A pre-commit
hook fails the commit if the Claude mirror drifts from the OpenCode
source.

Shared references live once under
`orchestrator/resources/opencode/skills/references/` and are mirrored to
both Claude sides (orchestrator-claude + skills-claude). See
`orchestrator/resources/opencode/skills/AGENTS.md` for the full table.

## Naming Convention

| Resource | Core (upstream) | Extended (local) |
|----------|-----------------|------------------|
| CLI | `openspec` | `openspec-extended` |
| Slash commands | `/osc-*` | `/osx-*` |
| Skills | `osc-*` | `osx-*` |
| Agents | n/a | `osx-*` |

Core skills (the upstream OpenSpec workflows) live in
`orchestrator/core/AGENTS.md` and are not modified locally.

## Resource Types

| Type | Path pattern | Frontmatter | Example |
|------|--------------|-------------|---------|
| Skill | `skills/<name>/SKILL.md` | `name`, `description`, `license` | `osx-workflow` |
| Agent | `agents/<name>.md` | `description`, `hidden`, `mode`, `temperature`, `permission` | `osx-analyzer` |
| Command | `commands/<name>.md` | `description` (OpenCode) | `osx-phase0` |

Only skills, agents, and commands are deployed. State I/O is done by
calling the binary's `osx` subcommand directly — no scripts or lib
files are shipped.

## Manifest (`manifest.toml`)

Each platform has its own manifest tracking the version of every
resource. Phase 4 keeps a **single unified manifest** per platform
covering both the orchestrator- and skills-side resources (the
single-file split happens in Phase 5):

```toml
[resources.skills.osx-workflow]
version = "0.5.0"

[resources.agents.osx-analyzer]
version = "0.2.1"
```

Skills can also declare which shared references they consume (from the
`skills/references/` pool) so the deploy copies them into the skill's
own `references/` folder at the target site. The shared pool lives at
`orchestrator/resources/opencode/skills/references/`. See
`orchestrator/resources/opencode/skills/AGENTS.md` for the full
semantics.

Versions are bumped **per resource** (not per release) by
`mise run version:update` — see root AGENTS.md "Version Bumping"
section.

## Conventions

- New resources get an `osx-` prefix; never collide with `osc-*` (core) names.
- One manifest entry per resource; CI fails on missing entries.
- Files under `orchestrator/core/` are not in this manifest — that tree is synced from upstream.
- Edit resources under `orchestrator/resources/opencode/` (orchestration side) or `skills/resources/opencode/` (skills side) only; the corresponding `claude/` subtrees are generated.
