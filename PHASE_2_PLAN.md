## Phase 2E — Phase 1 closure: single-tool exit-code propagation

**Bug.** `cli.py:1351-1354` raises `SystemExit(1)` for any single-tool failure, swallowing `SystemExit(2)` raised by `deploy_core` when `--with-core` refuses to overwrite without `--force`. The integration test `tests/integration/test_install_with_core_safe.py::test_existing_deploy_refuses_without_force` fails today (observed during Phase 1 review).

```python
# cli.py:1351-1354 (current, buggy):
total = len(successes) + len(failures)
if total <= 1:
    if failures:
        raise SystemExit(1)   # ← swallows e.code
    return
```

The multi-tool path (`raise SystemExit(1)` at `cli.py:1364`) is **correct semantics** — multi-tool signals "any of N tools failed" and the inner exit code is irrelevant. **Only the single-tool path needs the fix.**

**Fix.**

1. Change the failures data structure to carry an integer exit code:
   ```python
   failures: list[tuple[str, str, int | None]]   # (name, display_message, exit_code)
   ```
2. In install/update `except SystemExit as e:` blocks, capture `e.code if e.code is not None else 1` (bare `raise SystemExit` has `code=None`); in `except Exception:`, capture `1`.
3. `_summarise` single-tool branch: `raise SystemExit(failures[0][2])` (exit_code is `int`, never None at this point). Multi-tool branch keeps `raise SystemExit(1)`.

**Files touched:**
- `orchestrator/source/cli.py` (install/update loops and `_summarise`)
- `tests/unit/test_install_multi.py` — add `TestSingleToolExitCodePreserved` class

**Tests to add** (in `tests/unit/test_install_multi.py`):
- `test_runtime_error_yields_exit_1`
- `test_system_exit_2_yields_exit_2` — driven by mocking `deploy_all_resources` to raise `SystemExit(2)`
- `test_bare_system_exit_yields_exit_1` — the `raise SystemExit` form
- `test_multi_tool_system_exit_still_collapses_to_1` — confirms multi-tool semantics are unchanged

**Verification:**
- Existing `tests/unit/test_install_multi.py::test_install_single_tool_failure_exits_1` (RuntimeError path) continues to pass.
- Existing `tests/unit/test_install_multi.py::test_systemexit_propagates_as_failure` (multi-tool path) continues to pass.
- `tests/integration/test_install_with_core_safe.py::test_existing_deploy_refuses_without_force` flips to green.


### A.1 — New `{{SKILL_PREFIX}}` token (6th token)

`tools.py:_adapter_tokens` extends to 6 keys: `ASK_TOOL`, `DOCS_FILE`, `CMD_PREFIX`, `TOOL_NAME`, `PLATFORM_DIR`, **`SKILL_PREFIX`**.

**Token value per adapter:**
| Adapter | `SKILL_PREFIX` |
|---|---|
| opencode | `/` |
| claude | `/` |
| cursor | `/` |
| codex | `$` |
| kimi | `/skill:` |

**Source-file rewrite pass.** Every shipped resource that has literal `/osx-...` invocations gets `<prefix>osx-...` via `{{SKILL_PREFIX}}`.

| Tree | Files affected |
|---|---|
| `orchestrator/resources/opencode/commands/` | `osx-changelog.md`, `osx-maintain-docs.md`, `osx-phase0.md` through `osx-phase6.md` |

| `skills/resources/opencode/skills/osx-review-test-compliance/` | `SKILL.md`, `references/*.md` |

Grep before adding tokens:

The current `{{CMD_PREFIX}}` token resolves to `osx-`/`osx:` (filename prefix), **not** to `/osx-`. Those are two different things: the slash in `/osx-...` is the invocation prefix, which is what `{{SKILL_PREFIX}}` is now for.

### A.3 — Refactor `_build_claude_skill_from_command` into adapter-driven helpers

`_build_claude_skill_from_command` (`cli.py:329-360`) does **three** things; the plan originally only generalized (1). All three need to be expressed in `ToolAdapter`:

| Responsibility | Adapter field | Claude | Opencode | Cursor |
|---|---|---|---|---|
| (1) Strip `agent:` line | `agent_field_transform: Callable[[str], str] \| None` | `strip_agent_line` | `None` | `strip_agent_line` |
| (2) Inject `name: <name>` at frontmatter close | `inject_name_in_skill_mirror: bool` | `True` | `False` | `True` |
| (3) Unclosed-frontmatter fallback | inline edge case at call site (none required for current adapters) | n/a | n/a | n/a |

**New ToolAdapter field** in `orchestrator/source/tools.py`:
```python
inject_name_in_skill_mirror: bool
"""Whether the deploy step should inject ``name: <name>`` when emitting
the modern skill mirror. Claude Code's slash resolver needs it; tools
that derive the skill name from the on-disk directory (opencode) do not."""
```

**New module helper** in `tools.py`:
```python
def strip_agent_line(line: str) -> str:
    """Drop an opencode-only ``agent:`` frontmatter line."""
    return "" if line.lstrip().startswith("agent:") else line
```

**New ToolAdapter field** (also generalizes the `osx-` prefix strip):
```python
cmd_filename_strip_prefix: str | None
"""When non-None, the deploy step strips this prefix from the on-disk
filename before writing. Default ``'osx-'`` for shipped adapters; ``None``
to preserve the canonical name verbatim."""
```

Default for all shipped adapters: `"osx-"` (matches current convention).

**Refactored helper** in `cli.py`:
```python
def _build_skill_mirror(source_path: Path, name: str, adapter: ToolAdapter) -> str:
    """Render the modern skill mirror for a command file.
    
    Drives three adapter-controlled behaviours:
    - ``agent_field_transform`` strips opencode-only ``agent:`` lines.
    - ``inject_name_in_skill_mirror`` adds ``name: <name>`` for tools
      whose slash resolver reads it from frontmatter (Claude, Cursor).
    - inline fallback handles the rare unclosed-frontmatter case.
    """
```

The existing Claude test assertions (`test_deploy_claude_command_substitutes_claude_values`, `test_deploy_claude_skill_mirror_has_correct_path`) continue to pass — the rendered output is byte-identical.
